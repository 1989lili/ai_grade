# AI 阅卷性能与交互优化方案

> 状态：已实施 ✅　|　日期：2026-08-20 制定，2026-08-21 实施　|　目标：单次阅卷响应 ≤10s、客户端打包 ≤150MB、交互体验对标竞品

## 1. 背景与目标

当前自动阅卷流程（截图 → 智谱云端 OCR → 大模型评分）实测耗时 **30~40 秒**，主要瓶颈：

1. **智谱 GLM-OCR 云端手写识别**（multipart 同步上传，通常 5~15s）；
2. **评分模型全量生成后解析**（deepseek-v4-flash，prefill + 生成 10~25s）；
3. 两步串行，无并行无熔断。

竞品「教学小作坊」两种识别模式（视觉直评 / 独立 OCR）均能控制在 **5s 以内**，客户端 **130MB** 且启动快，全程有动态扫描动画、步骤提示、实时进度输出。

**本项目目标：**

| 指标 | 目标 |
|------|------|
| 单次阅卷响应 | **≤10s**（任何路径，超时自动熔断降级） |
| 客户端打包体积 | **≤150MB**（含本地 OCR 模型） |
| 启动速度 | onedir 免解压 + 懒加载，1~2s |
| 交互体验 | 全程可视化：扫描动画、OCR 文本实时上屏、评分流式输出、阶段耗时展示 |

## 2. 现状分析

### 2.1 当前流程与耗时构成（backend/app.py stream_analyze_card_grading）

```
截图+预处理(≈0.5s) → 智谱OCR云端识别(5~15s) → 评分LLM文本流式(10~25s) → 填分提交
```

- 前端已有基础：扫描动画（launcher.py TkScanLine）、NDJSON 状态流、token/reasoning 流式、partial_score 预展示、timing 埋点。
- 后端已有"多模态直评"代码路径（`build_grading_messages` 中 `ocr_text` 为空时直发图片），但主流程强制先走 OCR，未启用。

### 2.2 现有扫描动画问题（launcher.py TkScanLine）

- 纯色 4px 横线（#00f2fe）匀速移动，无渐变/光效/边框高亮，视觉单调；
- 单次扫描 900ms 与截图动作无联动（扫完即截图，无完成反馈）；
- 无方向自适应（固定自上而下）、无缓动（匀速机械感强）。

### 2.3 现有打包问题

- onefile 单文件模式：每次启动解压 32MB 到临时目录（`sys._MEIPASS`），冷启动慢；
- launcher.py / app.py 顶层大量导入大模块（webview、mss、pyautogui、PIL），拖慢进程启动。

## 3. 竞品分析（教学小作坊）

- **双识别模式**（教程原文）：模型自带 OCR 能力（如 GPT-4o / DeepSeek 视觉）→ 直接图片识别评分；否则启用自带 OCR（如 **llama-ocr-2.7**）→ 文本识别后交评分模型。
- 全程可视化：扫描动画、步骤提示、模型实时输出、状态栏（绿=就绪/红=未配置）。
- 客户端约 130MB、免安装、启动快；支持网络模型 / 本地模型；多评模式（多次评分取均值）。

**结论：** 竞品 5s 的实现 = 视觉模型一次调用（省一次网络往返）+ 本地/快速 OCR（1~2s）+ 流式输出。llama-ocr-2.7 为 2B 视觉模型（约 1~2GB），**超出我方 150MB 体积预算，不采用**，本地 OCR 改用轻量 RapidOCR。

## 4. 方案设计

### 4.1 双识别模式架构（识别器抽象）

```
┌─────────────────────────────────────────────────────────┐
│                    识别器接口 (recognizer)               │
│  recognize(image) → { text, words_count, meta }         │
├──────────────────────────┬──────────────────────────────┤
│  模式一：视觉直评（默认）  │  模式二：独立 OCR            │
│  GLM-4V-Flash             │  RapidOCR(本地, 默认)        │
│  截图→视觉模型一次调用     │  截图→本地OCR(1~2s)         │
│  返回：识别文本+分数+评析   │  →文本评分模型流式(2~4s)     │
│  耗时 ≈ 4~5s ✅            │  耗时 ≈ 4~6.5s ✅           │
├──────────────────────────┴──────────────────────────────┤
│  模式三：智谱云端 OCR（兜底，可选）                       │
│  高精度但慢，设 6s 超时熔断，超时自动降级本地 OCR          │
└─────────────────────────────────────────────────────────┘
```

**要点：**

1. 新增 `backend/recognizer.py`，定义统一接口与三种实现（vision / local_ocr / zhipu_ocr），可配置切换；
2. 视觉直评：GLM-4V-Flash（免费、首 token 快），复用智谱 key；复用现有 `build_grading_messages` 多模态路径，prompt 要求一次输出「识别文本 + 分数 JSON」，流式返回；
3. 本地 OCR：RapidOCR（onnxruntime CPU），手写识别模型约 15MB，可随包分发，离线可用；
4. 评分模型：非推理快速模型（glm-4-flash / deepseek-chat 关闭 thinking），流式输出；
5. 熔断机制：OCR 6s 超时自动降级、LLM 首包 8s 熔断（已有）、任何路径总耗时 ≤10s。

### 4.2 时间预算

| 路径 | 截图 | 识别 | 评分 | 合计 | 达标 |
|------|------|------|------|------|------|
| 视觉直评 | 0.5s | — | 3~4s（一次调用） | **≈4~5s** | ✅ |
| 本地OCR+文本评分 | 0.5s | 1~2s | 2~4s | **≈4~6.5s** | ✅ |
| 智谱OCR兜底+文本评分 | 0.5s | 5~8s（6s熔断） | 2~4s | **≈7~10s** | ⚠️ 边缘，熔断保障 |

### 4.3 前端配置（AI 配置页）

- 「识别方式」下拉：**视觉直评（快）** / **本地 OCR（离线）** / **智谱云端 OCR（准）**，默认视觉直评；
- 视觉直评时隐藏"OCR API Key"必填校验（当前 `missing_ocr_api_key` 强制拦截）；
- 模型选择联动：视觉直评 → 视觉模型列表（GLM-4V-Flash）；独立 OCR → 文本评分模型列表。

### 4.4 交互增强（让等待不焦虑）

1. **扫描动画优化**（launcher.py TkScanLine 重构）：
   - 视觉：扫描线改为**渐变光带**（青→白→青三段 Canvas 线模拟）+ 扫描头高亮；区域四角加**角标高亮**；
   - 动效：**正弦缓动**（起止减速），消除匀速机械感；扫描速度随区域高度自适应（大区域适当加速）；
   - 行为：扫描完成瞬间**边框闪烁一次**再截图（与截图动作联动，给"采集完成"反馈）；等待评分期间保留循环扫描；
   - 可选：支持横向扫描方向配置（兼容横向答题区域）。
2. **OCR 文本实时上屏**：本地 OCR 分块识别，识别出的文本逐行推送给前端展示（不等全部完成）；
3. **阶段进度条**：截图 ✓ → 识别 ✓ → 评分 ✓，每阶段完成打勾并标注实际耗时（复用 timing 事件）；
4. **评分流式**：token 打字机 + partial_score 分数预展示（已有，保留增强）；
5. **剩余时间预估**：首 token 到达后，基于流式速率估算剩余时间展示"预计还需 Ns"；
6. **流水线预截屏**：本轮评分进行时，并行截取下一张试卷图（点击下一张后立即可用），重叠 1~2s/张。

### 4.5 打包与启动优化

- **onedir 模式**：改为目录形态打包（免启动解压），启动快；目录体积 ≈ 单文件解压后大小，控制在 150MB 内；
- **懒加载**：launcher.py / app.py 顶层大模块（mss、pyautogui、PIL.ImageDraw 等）改为函数内 import；
- 本地 OCR 模型以 data 形式打包，路径通过 `sys._MEIPASS`/`sys.executable` 目录解析（兼容 onedir）。

## 5. 打包体积预算（本地 OCR 入包后）

| 组件 | 估算 |
|------|------|
| 现有客户端基础 | ~33MB |
| onnxruntime (CPU) | ~25~30MB |
| RapidOCR 模型（检测+识别+手写） | ~15MB |
| numpy / opencv-headless 等 | ~25~30MB |
| **单端合计** | **~105~125MB ✅ ≤150MB** |

> 优化手段：RapidOCR 使用 Pillow 后端可排除 opencv（再省 ~25MB）；模型量化可再减半。管理端不含 OCR，体积基本不变。

## 7. 风险与注意事项

1. **RapidOCR 手写精度**：中低年级手写体识别可能弱于智谱云端；对策：评分 prompt 已有 OCR 容错条款 + 识别文本实时上屏供人工核对 + 智谱云端作为可切换兜底；
2. **GLM-4V-Flash 精度**：视觉直评对手写复杂场景可能误判；对策：多评模式（同卷评 2 次取均值，可后续加）、用户可切回独立 OCR；
3. **onnxruntime 兼容性**：需在 Win7~Win11 实测（onnxruntime 较新版本可能要求更高系统版本）；
4. **onedir 迁移影响**：完整性校验（integrity.py）与资源路径解析需适配 onedir 目录结构，回归测试启动/升级流程；
5. **预设/配置兼容**：新增识别方式配置需兼容旧预设文件（缺省字段走默认值）。

## 8. 实测验证结果（2026-08-21）

### 8.1 响应时间（打包版 exe 实测，DeepSeek 评分）

| 路径 | 截图 | 本地OCR | 模型首响 | 评分完成 | 总耗时 | 结论 |
|------|------|---------|----------|----------|--------|------|
| local 首次（含模型加载） | 0.25s | 5.0s | 0.9s | 1.6s | **6.9s** | ✅ ≤10s |
| local 第二次（模型已加载） | 0.08s | 1.5s | 0.9s | 1.6s | **3.2s** | ✅ ≤10s |
| 打包版 local 全链路 | 0.09s | 1.9s | 0.9s | 1.9s | **4.0s** | ✅ ≤10s |

- **deepseek-v4-flash 推理模型坑**：默认只输出 reasoning 无 content，导致 30s+ 后报 model_empty_response；已通过 payload 加 `"thinking": {"type": "disabled"}` 修复（实测 1.1s 返回）。
- **cloud 熔断**：OCR_READ_TIMEOUT=6s，云端超时/网络异常自动降级本地 OCR（错误码全覆盖验证 ✅）；key 无效时快速报错不降级（265ms，明确提示用户 ✅）。

### 8.2 打包体积（onedir + UPX）

| 项 | 体积 | 说明 |
|----|------|------|
| 打包前（onefile 全量） | 263.3MB | cv2 111.8MB（含 ffmpeg 29.4MB） |
| onedir + 删 ffmpeg + UPX | **116.7MB** | ✅ ≤150MB，cv2 压缩至 20.4MB |

**踩坑记录：**
1. **onnxruntime DLL 初始化失败**：PyInstaller 收集到旧版 VC 运行库（vcruntime 14.36）与新版（14.44）混用 → 修复：spec 中统一从 conda 根目录打包全套 14.44 VC 运行库（过滤旧版后显式添加）；
2. **SSL 缺失**：打包版 https 请求依赖 libcrypto/libssl DLL，需在 binaries 显式加入（否则 deepseek/智谱 API 全失败）；
3. **UPX 需 --upx-dir 指定**（spec 内改 PATH 不生效，configure 阶段先于 spec 执行）；upx.exe 已下载至 tools/upx/；
4. **a.binaries 过滤/追加需用 3 元组 TOC**（dest_name, src_name, 'BINARY'），2 元组会导致 COLLECT 解包失败；
5. rapidocr_onnxruntime 1.4.x 模型在 `models/`（PP-OCRv4），旧 v3 hiddenimports 名称不存在需移除；模型路径基于 `__file__` 相对解析，onedir 下自动兼容。
